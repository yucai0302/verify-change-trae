# 示例输入

## 模式 B：验证一次改动（最常见）

> 用 verify-change 验证一下：我把登录页的「记住我」从 localStorage 改成服务端下发的持久化 token，改了 `src/auth/session.ts` 和登录页。期望：勾选后关掉浏览器再打开仍保持登录；不勾选则关闭后需重新登录；token 过期时要跳回登录页且不残留旧态。本地 dev server 已经跑在 5173。

可选补充：`重点验持久化和报错路径`、贴一段控制台日志、指出某个已知坑。

## 模式 A：首次建图

> 给当前项目建一份 feature map，先把登录、主导航、核心列表页这几个高频域建起来。

## 模式 C：全量回归

> 跑一遍全量回归，发版前想确认没把别的功能带崩。

## 复现 bug

> 用 verify-change 复现这个用户反馈：在列表页连续快速点两次「新建」，会生成两条重复记录。附上复现步骤和用户截图。

## 最小输入

只给一句也行：

> 验证一下这次改动。

此时 skill 会自己去读 diff / 变更文件、匹配 feature 条目、确认实例健康；确实缺信息时只问最必要的一个问题。

## 输入里不要给什么

- 不要给「应该没问题」这类预设结论，会污染取证。
- 不要给生产环境地址或真实用户数据；验证只在本地 / 测试 / 预发环境做。
- 不要把密钥明文贴进对话，用环境变量名指代。
