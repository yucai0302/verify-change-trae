# Proof bar：什么算合格证据

## 一句话

证据要能说服一个没参与这次改动的怀疑者：功能在真实用户路径上跑通了，而且副作用也对。

## 前置：健康检查

任何驱动之前先确认：

- 跑的是**本次改动之后**的构建 / 服务，不是旧进程、缓存 bundle 或别的实例；
- 记录一条可核对凭据：版本号、构建时间、启动命令输出、进程 / 端口、git HEAD，任选其一；
- 实例不新鲜就先重启。**stale 状态下收集的所有证据作废**。

## 五类路径

按改动的影响范围选，不必每次全跑；跳过必须写明理由：

| 路径 | 要看到什么 |
|---|---|
| 成功 | 触发动作后出现稳定的预期终态 |
| 取消 | 中途取消后状态回滚、无残留 |
| 报错 | 错误提示正确、可恢复、不吞异常 |
| 空态 | 无数据时不白屏、有明确引导 |
| 持久化 | reload / 切换离开再回来 / 重启后值仍在 |

## 合格证据

- 走**真实用户路径**：界面点击、注册的快捷键、菜单、正常后端链路、真实命令或 HTTP 请求。
- 触发动作和稳定终态在**同一次记录**里（同一段日志、同一次截图序列、同一段录屏）。
- **验副作用，不只验像素**：DOM 属性、剪贴板、网络 / RPC 日志、文件内容、数据库值、reload 往返，至少一项与行为直接对应。
- 状态检查（读 DOM、读变量值）只能用来**佐证**，不能代替用户路径。

## 不合格（明确禁止）

- 把「能打开」「页面看起来对」「构建通过 / lint 通过」当作功能通过。
- 直接调内部函数、直接改数据库、mock 掉渲染层或关键服务来制造「成功」。
- 用固定 sleep 等异步结果（要等可观察终态）。
- 截图只拍初始态或只拍成功态，没有中间过程。
- 把没跑到的写成通过；把推测写成观察。

## 不可达怎么报

统一格式：

```
路径 <名称> 未验证，原因：<账号 / 权限 / 环境 / 原生能力 / 外部依赖 / 无测试账号>，已改验 <最接近的真实路径> 作为替代。
```

明说被什么挡住，比悄悄跳过更有用——它告诉团队还缺什么环境能力。

## 发现问题之后

修 → 从健康检查重跑 → 直到通过或明确判定做不到。不允许「改成看起来能过」就收尾；判定做不到也要写清卡在哪一步、需要人提供什么。
