# 验证报告模板

文件名：`<项目根>/.verify/reports/YYYY-MM-DD-<slug>.md`
对话里先给一句结论，再给报告路径。不要只在对话里长篇描述而不落文件。

## 模板

```markdown
# 验证报告：<改动简称>

- 时间：
- 环境：本地 / 测试 / 预发；构建标识：
- 结论：**通过 / 有条件通过 / 未通过 / 无法验证**
- 结论依据（一句话）：

## 1. 改动范围与命中的地图条目
| 改动 | 命中的 feature 文件 | 匹配理由 |
|---|---|---|

未命中任何条目时：写明这是新增功能域，并给出补图建议。

## 2. 验证矩阵
| 路径 | 预期 | 实际观察 | 结果 | 证据编号 |
|---|---|---|---|---|

## 3. 证据清单
| 编号 | 类型 | 内容 / 路径 | 对应路径 |
|---|---|---|---|
| E1 | 命令输出 / 截图 / 日志 / DOM 快照 / 文件内容 |  |  |

## 4. 未覆盖与被挡住
- 路径 X 未验证，原因：…，已改验 …
- 本次未覆盖 …，理由：…

## 5. Feature Map 更新
- 新增条目 / 修正入口 / 新增坑：
- 发现的漂移：

## 6. 下一步
- 需要人处理的：
- 建议往 codebase / lint 层收的重复问题：
```

## 结论判定口径

| 结论 | 判定条件 |
|---|---|
| 通过 | 所有受影响路径都有合格证据，且副作用核对无误 |
| 有条件通过 | 核心路径通过，存在明确记录的非阻塞未覆盖项 |
| 未通过 | 存在实际观察到的偏差，必须附证据编号 |
| 无法验证 | 应用跑不起来 / 环境被挡 / 缺账号，且无法用最接近的真实路径替代 |

「无法验证」时**不要**用读代码推断代替结论。它和「未通过」是两件事，混写会让报告失去意义。

## 写作要求

- 每个「实际观察」写具体看到了什么，不写「正常」「符合预期」。
- 证据编号与验证矩阵一一对应，不留悬空引用。
- 报告里不贴大段日志原文，只贴关键行，完整日志放 `.verify/evidence/`。
- 第 5 节即使没有更新也要写「无」，用来证明地图被检查过。
