# Feature Map 规范

## 它是什么

codebase 是团队决策的投影，也是最可靠的记忆。Feature Map 是它的压缩索引：用行为级的短 Markdown，告诉 Agent「这个功能存在、用户怎么到达、怎么驱动、哪里会骗人」。目的是让 Agent 不必每次重新翻源码就能定位上下文，省 token。

它和 wiki 的区别（沿用原版 README 的四条）：

- **Scoped**：一次只打开与本次改动相关的一个文件，不读整个语料。
- **Actionable**：每个文件固定回答同样四个问题。
- **Sweepable**：`features/README.md` 从上到下就是全量回归顺序。
- **Maintained as code**：漂移和 UI 改动在同一个 PR 里修，或由一次建图巡检修。

## 文件结构

```
<项目根>/.verify/features/
├── README.md                        # 索引 + 基线前提 + 全量回归顺序
├── <feature>.md                     # 一个功能域一个文件
└── multi-surface-journeys.md        # 跨模块旅程，放最后
```

文件名用小写连字符，按**用户能说出口的功能名**命名（`sign-in.md`、`prompt-box.md`），不要按代码模块或组件名。

## 四段式条目模板

每个 feature 文件固定四个二级标题，顺序不变：

```markdown
# <功能域名称>

## 有什么（Sub-features）
- …

## 用户怎么到达（How to get to it, user POV）
- …

## 怎么驱动（Driving it with IDE capabilities）
| 目的 | 用哪个内置能力 | 观察到什么算到位 |
|---|---|---|
| … | … | … |

## 有什么坑（Gotchas）
- …
```

第三段是本 skill 对原版的关键改动：原版写「调哪条 control-atlas 命令」，这里写「用 IDE 的哪个能力 + 什么可观察状态算数」。没有自建 CLI 时，这一栏就是驱动契约，不能空着。

## 写作约束

- **行为级，不写实现**：写「Ctrl+K 打开命令面板并聚焦输入框」，不写 `CommandPalette.tsx` 的 props 结构。
- **够短**：单文件控制在一屏能读完（原版样例约 0.7~5 KB）。某一段开始需要自己的前置条件时，拆成新文件。
- **只记跑通过的**：驱动步骤只有亲自跑过并观察到预期结果才标 `已验证`；其余标 `未验证` 并写原因。错的驱动方式比没有更糟，因为 Agent 会照着做。
- **坑要具体**：写「流式输出非确定性，要等可观察终态，不要 sleep 固定毫秒」，不写「注意异步问题」。
- **不写密钥**：凭据只以环境变量名出现，例如 `$APP_TEST_PASSWORD`。

## README.md（索引）必须包含三段

1. **基线前提**：登录态、实例必须新鲜、隔离环境怎么区分、选择器偏好、哪些操作属于手工范围。
2. **全量回归顺序**：按「账号与外壳 → 主导航 → 核心功能 → 布局 → 外部依赖 → 设置 → 系统级 UX → 跨模块旅程」从上到下列出所有文件链接。这个顺序就是模式 C 的 sweep 顺序。
3. **条目契约**：指向四段式模板，说明新增条目必须遵守。

## 维护约定

- 和 UI / 行为改动在**同一个 PR** 里更新对应条目。
- 每次模式 B 验证结束，顺手把新发现的坑、失效的入口、新加的路径写回去。
- 定期（原作者建议每天）跑一次「地图巡检」：逐条对比当前代码与地图，标出漂移，实际跑一遍验证。**漂移不能靠改文档掩盖产品 bug**。
- 发现某类问题反复出现 → 不要只往 Gotchas 里堆，考虑往 codebase 架构或 lint 规则上收。按约束强度排序：codebase > static analysis (lint / compiler / CI) > rules / bug bot > skill > style guide，越靠前越能永久生效。
